Guía de activaciones manuales

Todo lo que queda pendiente en Mente en Foco ya no es código — es acción tuya en paneles externos (Supabase, Resend, Cloudflare, Stripe, Google Cloud) o una decisión jurídica. Esta guía está ordenada por prioridad real, con el paso a paso exacto de cada panel. Marca las casillas a medida que avances; el progreso se guarda en este navegador.

P0 — Backups / PITR

Crítico · bloquea todo lo demás
Lo ejecutas tú, en el panel de Supabase. Nadie más puede hacerlo. Hoy: pitr_enabled: false, 0 copias recuperables.

  1. Entra a supabase.com/dashboard y abre el proyecto Mente en Foco (ref eluxdqsprbgtnwznmxqe).

  2. Si el proyecto sigue en plan Free, súbelo primero. Ve a Settings → Billing (o Organization → Billing) y cambia a Pro (o superior). Asegúrate de que el compute quede en al menos Small — PITR lo exige.

    Esto tiene costo mensual fijo, además del add-on de PITR.

  3. En el menú lateral ve a Database → Backups y abre la pestaña Point in Time.

  4. Elige la retención. Recomendado: 28 días — es la ventana máxima, justificada porque los datos clínicos son irreemplazables y una corrupción puede tardar en detectarse.

    Referencia de precio (confírmalo en el panel al activar): 7 días ≈ US$100/mes · 14 días ≈ US$200/mes · 28 días ≈ US$400/mes.
    Al activar PITR, Supabase deja de tomar los Daily Backups — no corren los dos a la vez, es normal.

  5. Confirma el cargo y espera a que el panel muestre PITR activo con la primera copia física disponible (puede tardar un rato).

✅ Cómo confirmar que quedó bien

Desde la raíz del repo, corre:

node scripts/verify-pitr.cjs

Debe pasar de ⛔ GATE a ✅ OK cuando detecte pitr_enabled: true y al menos una copia recuperable.

🔒 Compuerta: hasta que el script confirme ≥1 copia recuperable, siguen bloqueados los DROP de test_scores y guides, y cualquier operación estructural irreversible futura.

P0b — Archivo legal de 15 años

Pendiente de diseño
PITR (arriba) no cumple esta obligación — son cosas distintas.

La Resolución 1995/1999 (mod. 839/2017) exige conservar la historia clínica 15 años desde la última atención. PITR es recuperación operativa de corto plazo (máx. 28 días), no un archivo de largo plazo. Falta definir un mecanismo de exportación lógica periódica cifrada, guardada fuera de Supabase.

Esto no es un simple "entra y activa" — necesita que decidamos dónde se guardan esos respaldos cifrados (¿un bucket S3/Backblaze aparte?, ¿con qué cifrado?, ¿con qué frecuencia?) antes de construirlo. Coordínalo con Cowork/Claude Code cuando quieras avanzarlo — no es un pendiente de esta guía de clicks.

P1 — Rotar Resend + verificar dominio

Alto
Lo ejecutas tú. La clave actual está comprometida y sin rotar desde el 19 de julio. R6 (más abajo) depende de que termines esto.

  1. Entra a resend.com/api-keys y crea una nueva API key (no borres la vieja todavía). Cópiala a un lugar seguro y temporal — no la pegues en este chat ni en ningún chat de IA.

  2. Ve a resend.com/domains → Add Domain → escribe tu dominio propio.

  3. Resend te da 3 registros DNS (SPF, DKIM, DMARC). Entra al panel de tu proveedor de dominio (o a Cloudflare DNS si el dominio ya vive ahí) y agrégalos exactamente como los da Resend.

  4. Vuelve a Resend → Domains y espera a que el estado pase a Verified (puede tardar de minutos a horas por la propagación DNS).

  5. Actualiza el secret en Supabase: Project Settings → Edge Functions → Secrets → edita RESEND_API_KEY con la nueva clave. Aprovecha y confirma que también existan SITE_URL y REMINDER_FROM_EMAIL (con tu dominio ya verificado, no un correo genérico).

  6. Con la nueva clave funcionando (prueba enviando un correo real desde la app), vuelve a Resend y revoca la clave vieja.

✅ Cómo confirmar que quedó bien

node scripts/verify-resend.cjs

Compara el updated_at del secret contra la fecha de la clave comprometida (19-jul) — debe mostrar una fecha nueva.

P1 — Cargar Turnstile (captcha)

Alto
Lo ejecutas tú. El código ya está escrito y publicado — solo faltan las 2 claves y el despliegue.

  1. Entra al dashboard de Cloudflare → Turnstile → Add widget.

  2. Asocia el widget a tu dominio, tipo Managed (el balance estándar entre fricción y seguridad). Al crearlo obtienes un Site Key y un Secret Key.

  3. En Supabase: Project Settings → Edge Functions → Secrets → agrega TURNSTILE_SECRET_KEY con el Secret Key. Nunca lo pegues en un chat de IA.

  4. En Cloudflare Pages/Workers (el proyecto de frontend) → Settings → Environment Variables → agrega VITE_TURNSTILE_SITE_KEY (Production) con el Site Key — este sí es público, va al navegador.

  5. Vuelve a desplegar el frontend (para que tome la nueva variable) y despliega el Edge Function actualizado:

    supabase functions deploy public-signup

✅ Cómo confirmar que quedó bien

node scripts/verify-turnstile.cjs

Cuando confirme que TURNSTILE_SECRET_KEY está cargado, avísale a Claude Code — hará una prueba de rechazo (request sin token → debe dar 403) sin crear ninguna cuenta real. El registro legítimo con el widget resuelto solo lo puede probar una persona en el navegador.

P2 — Retirar DEV_MAIL_REDIRECT

Bajo · depende de P1-Resend
Lo ejecutas tú, pero solo después de que el dominio de Resend quede Verified — si lo quitas antes, se rompe el envío de correo a personas reales.

  1. Confirma primero que completaste P1-Resend (dominio Verified).

  2. En Supabase: Project Settings → Edge Functions → Secrets → elimina DEV_MAIL_REDIRECT.

Avísame cuando lo hagas — Claude Code confirma por la Management API que ya no aparece en la lista de secrets.

P3 — Stripe a modo real (live)

Medio · go-live operacional
Lo ejecutas tú. El webhook ya está corregido (ya no genera contraseñas predecibles) — esto es pasar de pruebas a cobros reales.

  1. En el dashboard de Stripe, apaga el interruptor Test mode (arriba a la derecha).

  2. Ve a Developers → API keys y copia la clave pública (pk_live_...) y la clave secreta (sk_live_...).

  3. Recrea los Payment Links equivalentes a los de test (mismos planes/precios) ya en modo live, y actualiza stripe_links.json con las URLs nuevas.

  4. Ve a Developers → Webhooks → Add endpoint, apunta a la URL real del Edge Function stripe-webhook desplegado, selecciona el evento checkout.session.completed, y copia el signing secret (whsec_...).

  5. Actualiza los secrets en Supabase (STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET) y la variable de frontend VITE_STRIPE_PUBLISHABLE_KEY con los valores live.

  6. Haz una compra real de prueba (monto bajo) de punta a punta antes de anunciar el cambio: confirma que la cuenta se crea, llega el correo de recovery, y el plan queda asignado correctamente.

Hazlo después de P0 (backups) — si algo sale mal con datos reales de pago, quieres poder recuperar.

P4 — Dominio propio + Google Cloud

Medio
Lo ejecutas tú.

  1. Dominio → Cloudflare Workers: en el dashboard de Cloudflare, entra al proyecto (Workers & Pages) → Settings → Domains & Routes → Add → Custom domain, escribe tu dominio y sigue las instrucciones de DNS (si el dominio ya está en Cloudflare, se conecta automático).

  2. Espera a que el certificado SSL se emita (unos minutos) y confirma que el sitio carga en el dominio nuevo.

  3. Google Cloud (para el login con Google): entra a console.cloud.google.com/apis/credentials → tu proyecto OAuth → en OAuth consent screen, agrega el dominio nuevo como Authorized domain.

  4. Si Google pide verificar la propiedad del dominio, usa Google Search Console (método DNS TXT es el más simple).

  5. En Credentials → tu OAuth Client ID, agrega el dominio nuevo a Authorized redirect URIs (con la ruta de callback de Supabase Auth) y a Authorized JavaScript origins.

  6. Actualiza SITE_URL (secret de Supabase) y cualquier referencia de URL fija en el frontend al dominio nuevo.

P5 — Revisión jurídica

Legal · no es un panel
Esto no se resuelve con clicks — necesita un abogado especializado en protección de datos / salud en Colombia.

  1. Reúne los 3 documentos que necesitan revisión: la política de tratamiento de datos general (Ley 1581/2012), el texto del consentimiento clínico (Ley 1090/2006 — ya construido y en uso, texto pendiente de validar), y el consentimiento de vínculo empleado↔empresa del backend B2B (ya construido, inerte, texto en borrador).

  2. Comparte con el abogado también la Guia_R1_Backups_PITR.md (menciona la obligación de retención de 15 años) para que confirme si el mecanismo de archivo propuesto es suficiente.

  3. Cuando tengas el texto final aprobado de cada consentimiento, avísame — actualizamos el copy en el código y activamos el vínculo B2B (hoy sigue inerte a propósito).

Regla firme mientras avanzas esta guía: no se declara el sistema "production-ready" ni se reabren los DROP aplazados de test_scores/guides mientras P0 no esté cerrado. El detalle técnico completo de cada punto vive en 01_ROADMAP_Y_TAREAS.md y en contexto-proyecto/auditorias-tecnicas/.
